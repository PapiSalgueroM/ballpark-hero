## 4. How the day's bugs were actually found, because the method transfers

Every defect in section 1 shares a shape: **the game works, nothing throws,
nothing logs, and the only evidence is somewhere nobody looks.** Four questions
found all of them. Ask them about anything.

1. **"What does a crawler actually receive?"** Not what the code generates,
   what is in `public/<route>/index.html`. Rounds 371, 372 and 373 are all
   "correctly generated, never shipped". A check that reads the source cannot
   see what the output dropped.
2. **"Which tables are empty, and is that explicable?"** This found Round 375
   (a write that was never sent), Round 377 (a badge nobody can win) and Round
   378 (the locked admin screen). Run it again in a month.
3. **"Does the code's name for a thing match the data's name for it?"** Round
   374 (six columns that do not exist), Round 376 (slugs the registry cannot
   resolve), and 3.1 and 3.2 above.
4. **"Is this claim measured or assumed?"** Round 379's fix looks like it should
   have been "retry harder". Measurement showed a 3-second retry recovers
   **none** of 14 attempts, because it is a daily quota. The right fix was
   somewhere else entirely.

## 7. Two habits that would have saved the most time today

**Measure before you fix, and measure the output not the source.** Three rounds
today were "the data was always right, the delivery was broken". A source-level
check would have passed on all three for months.

**Write the negative control before you believe the harness.** Two harnesses I
wrote today reported success while broken: one read a cache table that RLS
returns empty, and one installed a DOM observer before the DOM existed. Both
failed in the *same shape as the bug they were testing for*, which is the most
dangerous way for a check to be wrong. If a control cannot make your harness go
red, the harness is decoration.
