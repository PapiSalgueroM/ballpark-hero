## 1.2 How code reaches the live site

Three separate steps, and skipping the third is a known way to serve a stale site for weeks:

1. **Commit and push to `main`.**
2. Lovable syncs the commit and rebuilds its **preview**.
3. **`deploy_project`** publishes to douknowball.com. Nothing a visitor sees changes until this
   runs. Verify with `get_project`: `latest_commit_sha` should match your head.

## 1.3 The gates a round must pass

```
node_modules/.bin/tsc --noEmit -p tsconfig.app.json     # plain tsc is a NO-OP, always exits 0
npx vite build                                          # or npm run build:seo for snapshots
node scripts/runAllSims.mjs                             # 188 harnesses at time of writing
```

If the round rebuilt `dist` or the `public/` snapshots, also run all 15 built-site fences:
`simAdsense simBrand simHeadTags simHiddenPages simHubs simIndexNow simIndexing simInternalLinks
simNoRivalNames simPrerender simPrerenderBoot simRetiredRoutes simSchema simSitemap
simSnapshotAssets`.

**`runAllSims` buffers its output.** A file with one line saying `Running 188 node harnesses` is
a run in progress, not a hung one. It prints everything at the end. This cost time twice in this
session; do not misread it as a stall.

## 1.5 Rules that must never break

Full list in `CLAUDE.md`. The ones that bit during this session:

- **Validators fail closed.** Never reintroduce accept-on-error.
- **Nothing computed from a clock goes into a saved page.** Snapshots in `public/<route>/` are
  photographs held for weeks.
- **A guard that reads source must read the CODE, not the comments.** Strip comments before
  matching, or the prose explaining the check satisfies the check.
- **Every check needs a negative control, and the control must be proven to change something.**
  A control that rewrites a string the file does not contain is green for the wrong reason.
- **Never evaluate an imported value at module scope.** That is how an import cycle got in.
- **Never draw from `Math.random` inside a `useState` initialiser.** Use `src/lib/firstDraw.ts`.
  React can discard a render and retry, and the retry draws again. See Round 421.

## 2.2 Round 420: a failed write must not delete a shipped artifact

Hit for real while building 419. The prerenderer failed to write
`public/nfl-higher-lower/index.html` with a Windows UNKNOWN error and left the snapshot
**deleted**, not stale, because a plain `writeFileSync` truncates its target before writing a
byte. That build exited 1 so nothing shipped, but that is luck about WHEN the write failed.

`scripts/lib/atomicWrite.mjs` writes to a temp beside the target and renames over it. Widened
once the class was understood: `genSitemap.mjs` (both `public/sitemap.xml` AND the
`scripts/data/lastmod.json` ledger), `genRetiredStubs.mjs` and `genHiddenStubs.mjs` all wrote the
same way. **The ledger is the worst case**: `CLAUDE.md` says losing it re-dates all 137 pages.

**The rename needed a retry, and only measuring said so.** Over 1,000 writes to one target, 8
failed with EPERM because something outside the project (a scanner, the indexer, a sync client)
held the file for the instant the rename happened. Across 145 routes that is more than one dead
build per prerender. One immediate retry barely helped (still 14 in 1,000). Five attempts with a
1, 2, 4, 8ms backoff failed **0 of 1,000**, and 993 still landed first try. A genuine error is
not retried.

**The trade taken on purpose:** if a holder never lets go the build stops where the old write
would have succeeded (measured 20 of 20 with a handle held open). Stopping with the page intact
beats deleting a live snapshot. **There is deliberately no truncating fallback.**

## 2.3 Round 421: a block must not be dropped from a snapshot by a race

The four connect 4 pages pick their board with `useState(getRandomConnect4Board)`, and
`prerender.mjs` seeds `Math.random` so a random pick freezes identically in every build. That only
holds if the draws happen in the same ORDER every time.

**React does not promise a `useState` initialiser runs once.** It can begin a render, throw the
work away and start again, and the retry drew AGAIN, advancing the shared generator and handing
back a different board. Measured with a counter and a stack on every draw: **8 draws when the
initialiser fires once and 9 when it fires twice**, draws 0 to 7 byte identical every run, the
ninth from that very line, 0.5178 giving Passports and 0.2038 giving Silverware. Proven a race
rather than the calendar by repetition: the same route at the same clock sample gave 8 on one run
and 9 on the next.

Fix is `src/lib/firstDraw.ts`, which holds the pick from the first render attempt to the commit
that survives and releases it there. Used at 10 sites. `scripts/playRenderStability.mjs` renders
every route 5 times at the SAME clock and fails if the readable blocks differ.
`simPrerender` section 16 enforces the rule at source level with a `RAW_RANDOM_BASELINE` ratchet:
**24 files still do this and are frozen in that list**, anything new fails, and a fixed file must
leave the list.

**Three wrong theories were committed as dead along the way.** That is deliberate: an unkilled
hypothesis costs the next round a day.

## 2.4 Round 422: your salary must reach your bank account

**Reported by the owner playing `/nfl-my-career`:** "none of my money is going into my account.
It just keeps going into the negatives even when I am making 30 million dollars a year."

He was right, and it was in **all four My Career games**. One line ran every season:

```js
c.netWorth = Math.round(((c.netWorth ?? c.earnings * 0.45) - upkeep) * 10) / 10;
```

It subtracted living costs and **added nothing**. The `?? earnings * 0.45` fallback only fires
while `netWorth` is undefined, so it paid out exactly once, on the first season. The
`if (upkeep > 0)` gate hid the other half: a player who buys nothing has no upkeep, so his net
worth never moved off his signing bonus no matter what he earned.

Measured on his exact case, 8 years at 30m with 2.5m upkeep: used to drift negative, now ends on
**88.1m** (88.3, 88.4, 88.5 for NBA, MLB, NHL).

**Existing saves are repaired, and that is safe rather than a guess.** A purchase is refused when
it costs more than you hold, so spending can never take a player negative. Only upkeep charged
against income that was never banked could, which is exactly this bug. So a negative balance is
ALWAYS the defect and never a debt the player chose.

**Why nothing caught it, the transferable lesson:** the money harnesses touch `netWorth`
constantly and could not have found this. They **inject** a starting balance (`simMoney` uses 50,
`simNflCareer` uses 300) so accumulation is never exercised, and `simMoney`'s only assertion is
that it must not fall below **minus 3 million**, which tolerates the bug outright.
`scripts/simCareerBanking.mjs` starts a real career from its real signing bonus instead.

## 2.6 Round 424: Stadium Tycoon's match was never played

The worst defect found in this session, shipped and live. `src/lib/stadiumTycoon.ts` computed
elapsed match minutes as:

```js
Math.floor((st.minute * MIN_LEN + dt) / MIN_LEN) - st.minute
```

`st.minute` is an integer, so that reduces to `Math.floor(dt / MIN_LEN)` with the remainder
recomputed from `st.minute` every call and **thrown away**. The hook ticks as soon as its
accumulator passes 0.2s, so `dt` is about a fifth of a second, `Math.floor(0.2 / 1.4)` is 0, and
the answer was 0 on every tick, forever.

**For a player:** the scoreboard read "YOU 0 - 0" at minute 0 for the entire life of a save and
the footer read "match #1". No goal was ever scored, so no goal bonus was ever paid, no win, no
streak, no division. The Squad track, 200 levels sold on "more goals, longer win runs", was a
pure money sink that provably did nothing. Idle income still ticked, so the game looked alive
while its entire match loop was dead.

**Why nothing caught it:** every existing check drove `tick()` with a big `dt`, and a big `dt` is
the one shape that HIDES this, because at `dt = 60` the floor is 42 and the clock looks perfect.
`scripts/simTycoonClock.mjs` reads the tick threshold out of `useStadiumTycoon.ts` rather than
hard coding it and drives the engine at that real cadence.

## 2.8 Round 426: the CFB dynasty stopped bricking at season five

**Blocker 2 of 7. Two commits, deliberately separate.**

**Part one, the guard.** `heismanRace` can legitimately return an EMPTY array, and two places
indexed `[0]` without checking. `CfbDynastyBoard.tsx:90` did it inside the final week handler, so
the throw happened before the season advanced or the state saved: the week, record and button
never changed, reloading restored the same dead week and crashed again, and the only remaining
control was "Fire yourself and start over", which deletes every season played. Line 198 did the
same in the recap.

**Part two, the real cause.** The offseason refill read:

```js
pos: ROSTER_SHAPE[t.players.length % ROSTER_SHAPE.length]
```

`ROSTER_SHAPE` is `['QB','RB','WR','WR','TE','OL','OL','DL','DL','LB','DB','DB']`. Skill
positions are indices 0 to 4. The refill runs from `t.players.length` up to 12, so any team
keeping 5 or more players could only ever draw index 5 and up: **linemen and defenders**.
Seniors graduate and elite juniors declare every offseason, so quarterbacks, backs and receivers
drained away and were never replaced.

**Measured over 12 seasons, same seed, only this line differing:**

| Season | Before: my roster | Before: skill players on the board | Before: Heisman |
|---|---|---|---|
| 2026 | QB1 RB1 WR2 TE1 OL2 DL2 LB1 DB2 | 176 | awarded |
| 2027 | QB1 RB1 WR1 TE1 OL2 DL2 LB1 DB3 | 144 | awarded |
| 2028 | QB1 RB0 WR1 TE1 OL0 DL3 LB2 DB4 | 90 | awarded |
| 2029 | QB0 RB0 WR1 TE1 OL0 DL3 LB1 DB6 | 43 | awarded |
| **2030** | **QB0 RB0 WR0 TE0 OL0** DL4 LB2 DB6 | **0** | **NONE** |
| 2031-2037 | all zero skill and zero OL | 0 | NONE |

**No Heisman in 8 of 12 seasons, and the first empty race is 2030, the fifth season, exactly the
year the reported brick happens.** After the fix the roster holds at the intended shape in all 12
seasons, the board holds 176 skill players throughout, and a Heisman is awarded 12 of 12.

The rng draws are unchanged in count and order, so this only moves which position a freshman
plays.

## 2.9 Round 427: the Player Stock Market Daily mode can be started

**Blocker 3 of 7. Three commits plus a revert, and the revert is the interesting part.**

**Symptom:** clicking "Daily market" always landed on "Couldn't open the market right now. The
full value history needs a connection." The request went out as
`year=in.(NaN)` and Postgres returned HTTP 400, `invalid input syntax for type integer: "NaN"`.

**Root cause, measured not reasoned:** `dailyPrngSeed('2026-09-03')` returns **-54366920**.
The hash coerces with `>>> 0` at every step except the last one:

```js
h ^= h >>> 16;                    // signed, no >>> 0 after it
return (h % 2147483646) + 1;
```

`^=` yields a SIGNED 32-bit result, so a set bit 31 makes the whole thing negative. Then
`START_YEARS[seed % 5]` indexes negative, returns `undefined`, and `undefined + i` is `NaN`.
**15 of 40 consecutive dates produce a negative seed; 14 of 40 left Daily mode unstartable.**
About 35 percent of days.

**Part one added the missing `>>> 0` and was REVERTED.** It is correct in isolation but nine
games seed off that hash, and `simDaily` caught the consequence: **Sign the Player then repeated
the same board four days running around day 69.** Reshuffling eight games' puzzles to fix one is
the wrong trade. The revert is `e4890a5f`.

**Part two, kept:** `startYearFor` is defensive. It wraps the modulo into range and falls back to
the first year on a non-finite seed, so a stray seed can never again become a silent 400.

**Part three, the shipped approach:** normalise with `>>> 0` inside `dailyCampaignSeed` only, and
record the trap at `dailyPrngSeed`'s return without changing its behaviour. The note says what it
does, that it can return negative, and that **callers must not index an array with it directly**.

**Measured after:** 40 dates, 0 with no valid year. **26 working days unchanged, 14 broken days
fixed, 0 working days changed**, because `>>> 0` is the identity on a positive seed.

**Why only one game was affected:** the six PRNG consumers each fold a non-positive seed back
into range themselves (`if (s <= 0) s += 2147483646`). Only the one caller that used the seed as a
raw array index ever showed it.

# PART 6: LESSONS, TRAPS AND THINGS THAT COST TIME

This is the part most worth reading. Every item here was paid for in this session.

## 6.1 The defect this session kept finding in its own work

**"The code changed and the words did not."** It happened at least eight times: a round entry
describing a mechanism the code does not have, a fence comment quoting numbers the file no longer
measures, a harness header claiming a runtime seven times faster than measured, a module doc
saying a memo releases on unmount when the code releases at commit.

The habit that catches it: after changing code, re-read every comment and doc line that describes
what you changed, and correct them in the same commit.

## 6.2 Withdrawing a claim you cannot substantiate

While playing `/perfect-season-nfl`, a rating badge read as "86" off a 0.6-scale screenshot while
the roster showed 99, and it was reported as a data mismatch. Checking properly: the only
text-extracted comparison (Hopkins 78 to 78) transferred correctly, and the ratings are computed
from Supabase at runtime so they are not in `src/` to check statically. **The claim was withdrawn
rather than reported.** The owner called this the most valuable part of that run.

The rule: **a pixel read is not a measurement.** If the only evidence is a screenshot, either get
text or drop the claim.

## 6.3 An unkilled hypothesis costs the next round a day

Round 420 recorded a plausible theory and left it standing. It had to be tested and disproved
before the real cause could be found. Round 421's commit then pointed the next round at four
routes on a hunch, and that lead was killed with evidence already in hand
(the blocks they drop are daily puzzle content, and they ROTATE with the date across builds).
**Write the hypothesis down, then kill it explicitly.**

## 6.4 Harness bugs found while writing harnesses

Three in a single retest, all of which made a working fix look broken or an empty run look green:

- These Connections games take **five** tiles per guess, not four.
- The mode row ("Daily", "Unlimited") was being clicked as if the buttons were tiles, which
  switched mode instead of selecting.
- **A synthetic `element.click()` from inside `page.evaluate` does not register** as a selection
  in these games. Use real Playwright mouse clicks.

Also: a first draft measured a rate with `st.minute` alone, which RESETS when a match ends, so it
read 10 after 140s and called a working clock broken. **The check was wrong, not the code.**

## 6.5 The browser pane is unreliable, do not fight it

The in-app browser pane went to a 0x0 viewport, a black screen and a hidden state repeatedly.
`requestAnimationFrame` does not run in a hidden pane, so any game driven by rAF (Stadium Tycoon)
appears frozen and is not. Symptoms to recognise: `Viewport: 0x0` from `read_page`, a click that
"could not be attributed to a frame", a screenshot that is entirely black, an `await` on rAF that
never resolves.

**Use refs from `read_page`, not screenshot coordinates**, because the pane scales the viewport
(1280x720 content shown in an 800x455 frame) and coordinate maths silently misses.

When the pane misbehaves, switch to headless Playwright via
`scripts/lib/playwrightLoader.mjs` and serve `dist` with `scripts/lib/hostLikeServer.mjs`.
`npx serve -s` never serves a prerendered route correctly.

## 6.6 Measuring at the cadence the game really uses

Round 424's bug existed **only** at the real tick rate. Every existing check drove `tick()` with
a big `dt`, which is the one shape that hides it. The harness now reads the tick threshold out of
the hook rather than hard coding it, so it cannot drift into testing a cadence the app abandoned.

**Generalise this:** drive the engine the way the app drives it, and read the parameters from the
app rather than restating them.

## 6.7 A test that injects the answer cannot find the bug

`simMoney` starts careers with `netWorth: 50` and only fails below **minus 3 million**. It could
never have found a game that pays nobody. If you are checking an economy, **assert that money
ARRIVES**, not just that it is finite and not catastrophically negative.

## 6.8 Windows and this repo

- `renameSync` over an existing file fails **EPERM** when anything holds a handle on the target.
  Retry with a short backoff; measured 8 failures per 1,000 without one, 0 with five attempts.
- Python heredocs eat backslashes. `/\\/g` in a `<<'PY'` heredoc becomes a literal newline in the
  emitted JS and breaks the regex. Use the Write tool for anything with escapes.
- `npx --no-install esbuild ... --alias:@=<ROOT>/src` with `shell: true` is the working recipe for
  bundling a `src/lib` module for headless testing.
- If you patch a source file for a control, write the patched copy **beside the original inside
  `src/lib`**, or its relative imports will not resolve. Delete it afterwards.
- Bundling anything that reaches the Supabase client needs a `globalThis.localStorage` stub.
- The repo shows roughly 642 modified files on his machine from CRLF alone. Prove with
  `git diff --ignore-cr-at-eol --stat`. **Never commit them.**

## 6.9 The suite has flakes, and they should be named as flakes

Three DB-dependent harnesses failed transiently under load during this session
(`simPlayerBingoPool` with a Postgres 57014 statement timeout, `simPlayerSearchAccents` with an
unreachable Supabase, and once `simLeaderboardCaps` for a real reason). Each passed alone
immediately after. **Record them as flakes rather than quietly re-running until green**, and note
that `simPlayerSearchAccents` fails closed correctly by printing "NOTHING WAS CHECKED".

is commented out, so the page is reachable and unlisted. That is exactly the shape a source
derived list misses and a player still finds.

streak with no natural ceiling, and every other higher-lower cap already equals its own observed
maximum because the cap clamps what gets stored, so deriving a number would be circular. A null
denominator is the documented behaviour in `docs/LEADERBOARD-SECURITY.md`.
Migration: `supabase/migrations/20260903_caps_allowlist_higher_lower_transfers.sql`.
