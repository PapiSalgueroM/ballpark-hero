# Career fallback bake, 2026-09-11 (Round 531, piece 2)

`src/data/careerPlayers.ts` is now GENERATED by `scripts/bakeCareerPlayers.mjs` from the live
`career_players` and `career_seasons` tables, read exactly the way `src/lib/fetchCareerPlayers.ts`
reads them (players ordered by name, seasons paged 1,000 at a time ordered by player id then
sort_order, assists left null where the league did not record them). `scripts/simCareerFallback.mjs`
fails when the file differs from a fresh bake. This file is the evidence for what changed.

Nothing was written to the database. No value in the file was typed by hand: every row is the
table's row. Where the table disagrees with a publisher, that is recorded below as a finding for
the desktop lane, which owns database writes.

## Findings for the desktop lane (nothing here was changed by this piece)

1. **career_seasons has no single stat convention**, and the 18 rows above that the table
   "corrected" since the file was typed mostly match neither the league nor the all competitions
   figure. Recommendation: decide one convention for the table, then re-source these rows and
   Ronaldo's Saudi rows. The bake will follow whatever the table says; `simCareerFallback` will
   go red until it is re-run after any table change, which is the point.
2. **Cristiano Ronaldo 2022-23 is missing from the table.** Verified with two publishers: he
   played 10 Premier League matches and scored 1 goal for Manchester United in 2022-23 (Wikipedia's
   2022-23 Manchester United season page gives the 22 November 2022 departure; StatMuse gives 10
   appearances, 1 goal, 0 assists), and he joined Al Nassr on 30 December 2022 (Wikipedia). His
   all competitions Manchester United line and his Al Nassr 2022-23 line each reached me from one
   source only (search snippets), so they are NOT stated here and no migration is written. To add
   the row honestly the desktop lane needs a second publisher for the Al Nassr half and a decision
   on finding 1 first, because the row has to be written in the table's convention.
3. **Transfer Path fallback puzzles tp-5 and tp-14 are now beatable on the fallback pool.**
   `src/data/transferPathPuzzles.ts` was derived from the 151 player file; on the 253 player file
   two puzzles have a shorter chain. `simTransferPathHints` section 2 and `simTransferPathModes`
   section 2 (classic and europe) report exactly this and are left red on purpose:
   - tp-5 Steven Gerrard to Cristiano Ronaldo: file says 3 (Gerrard, Luis Suárez, Gerard Piqué,
     Ronaldo, "The first was at Liverpool ... the last was at Manchester United"); the pool says 2:
     Gerrard, Xabi Alonso, Ronaldo (Liverpool, then Real Madrid).
   - tp-14 Mohamed Salah to Zlatan Ibrahimović: file says 3 (Salah, Federico Chiesa, Angel Di
     María, Ibrahimović, "... the last was at PSG"); the pool says 2: Salah, Ashley Cole,
     Ibrahimović (Chelsea, then LA Galaxy).
   The fix is `node scripts/genTransferPathHints.mjs`, which rewrites the fallback puzzle file
   from the current fallback pool, but see finding 4: the generator refuses to run until that is
   decided.
4. **Thirteen more verified active identities.** `scripts/lib/transferPathActiveIdentities.mjs`
   takes its candidate pool from `careerPlayers.ts`; with 253 candidates instead of 151 it finds 91
   safe identities, not 78. `simTransferPathActiveIdentity` section 1 lists the 13 (Alexis Mac
   Allister, Bruno Guimarães, Cody Gakpo, David Luiz, Emiliano Martínez, Jordan Henderson, Juan
   Mata, Julián Álvarez, Lautaro Martínez, Luis Díaz, Michael Olise, Ollie Watkins, Vitinha) and
   section 3 the 11 of them without a nationality annotation in `scripts/data/transferPathPull/careers.txt`.
   These are real teammates the Active Players Only rule could accept and does not. Regenerating
   means moving the generator's 78 identity and 203 puzzle guards on purpose, a new
   `transferPathVerifiedActive.ts`, re-annotating `careers.txt`, and a new dated restore migration
   (the generator refuses to rewrite the existing one). That is Transfer Path's call, not this
   piece's; the harness is left red rather than weakened.
5. `simTransferPathRepeat` reports "vitest did not report" in this worktree because it spawns
   `ROOT/node_modules/vitest/vitest.mjs` and the worktree carries only `.bin` shims. The test
   passes when run through the main tree's vitest (2 tests, 2 passed). Environmental, not a
   regression.

## One harness changed on purpose

`scripts/simCareerSeasonTruth.mjs` section 2 read "the current fallback contains no 2025-2026
row". That rule was right for a hand typed file whose every 2025-2026 row was a projection. The
baked file carries the 27 researched 2025-2026 tuples the same harness pins on LIVE in section 5,
so section 2 now requires the fallback's 2025-2026 rows to equal exactly those 27 (by the same
tuple key, in both directions) and still requires every one of the 77 quarantined tuples to be
absent. The `fallback` control (restoring one quarantined tuple in memory) still turns only
section 2 red. Green live: 27 exact live tuples checked.
