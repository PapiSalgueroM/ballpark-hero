**One open item in 271, deliberately not fixed.** `simHalftime` section 1 failed
once on the board ("splitting the match into halves moved the league by 7.47
points on its own"), then passed alone, and had passed on the Round 270 board.
The check is `gap > 3 * se` over `RUNS = 60`, so 7.47 is about four sigma and
should not appear once in four boards by chance. **The rate was not measured
because one run takes about 475 seconds and a 40 run sample is over five hours.**
Left alone on purpose: the rule is widen or seed, never loosen, and raising RUNS
would SHRINK three standard errors and make the test stricter, which is wrong if
there is a real bias and pointless if there is not. Run it overnight printing the
arm means, sd and gap, find out whether the gap centres on zero, then decide.

## Open security work, started 2026-08-22, NOT finished

Anthony asked me to "protect douknowball" and pointed at an Instagram post I
could not open (Instagram blocks automated fetching and routing around that is
not allowed). **Ask him what the post said, it may redirect all of this.**
In the meantime I audited the database, and one finding is serious.

**The World Leaderboard can be forged by anyone.** `global_leaderboard()` scores
as `100 * day_best / max(score for that game)` and computes the denominator from
`public.game_completions`, which takes anonymous INSERT with `WITH CHECK (true)`.
The openness is intentional and fine (guest-first tracking, no PII, see
`src/lib/completions.ts`); the defect is that the ranking treats forgeable data
as authoritative. Post one row for a game name that does not exist with a score
of 1 and you collect the full 100 points, repeatable per (game, date) pair.
**Measured: not exploited. 105,595 rows, no game's max above 5x its own p99.**

The fix is written and **NOT applied**, at
`supabase/migrations/20260822120000_leaderboard_score_caps.sql`. Verified read
only against live data: 0 players' points change, largest change 0, one row
dropped and it is `QA-Harness-Test` from July. Its first draft was WRONG (it
would have silently zeroed eight live games) and the whole story, including the
source-keys-versus-data-keys diff that caught it, is in `docs/PROJECT-STATE.md`
under the open roadmap items. **Read that before touching any of it.**

**The blocking question, which is why it is not applied:** a database change
takes effect immediately and does not go through the bat pipeline where Anthony
gets to look first. He was asked whether a cloud session may change the live
database directly and had not answered. Do not apply it on his behalf without
that answer.

Everything else came back healthy: 525 advisor lints and **zero at error level**,
RLS on every table, no anonymous writes to anyone's personal data, no CREATE
rights in the public schema for any public role, `has_role` already pinning its
search_path. Two one-click items are his alone: turn on Supabase leaked-password
protection (currently OFF) and confirm the spend cap is still on.

Two things this fix does NOT solve, each needing its own round: the crowd-vote
games can still be ballot-stuffed, and nothing rate limits writes, so someone
could grow the database until the spend cap trips. Neither is fixable in row
level security; both need an edge function in front of the insert, or a WAF.

| Reason | Source | Verdict |
|---|---|---|
| Page with redirect | Website | **Expected.** Eight routes are deliberate redirects for retired games. `genSitemap.mjs` already excludes them. Leave alone. |
| Crawled, currently not indexed | Google systems | **The empty-shell problem.** Should improve as Google recrawls. |
| Redirect error | Website | **The one worth investigating.** Source is ours. NOT diagnosed. |
| Discovered, currently not indexed | Google systems | Google knows the URL and has not crawled it. What 266, 268 and 270 attack. |

**The open lead.** The redirects in `App.tsx` are `<Navigate>` elements, so they
are **client-side**: a crawler requesting `/world-cup` gets HTTP 200 and whatever
`dist/index.html` holds, then JavaScript navigates. Those routes are excluded
from the sitemap, so the prerenderer never wrote a snapshot for them and they
serve the SPA fallback, which since Round 257 carries the home page's static
block. A crawler at `/world-cup` may therefore be reading home page content at a
redirect URL, which would plausibly produce both "Page with redirect" and
"Redirect error". **This is a hypothesis, not a finding.** There is a
`public/_redirects` file that was never inspected. Check what the live site
actually returns for all eight redirect routes before changing anything.

## Rules that will bite a fresh session

All in `CLAUDE.md`, but these are the ones that cost real time:

- **No em dashes or en dashes anywhere.** Code, comments, commit messages, site
  copy, messages to Anthony. He reads them as AI writing.
- **Data correctness before everything.** Never invent a player, stat, transfer
  or result. Two-source verify. Mark thin data rather than filling it.
- **Never put invented words in a real person's mouth.**
- Never read `VITE_SUPABASE_*` env vars, they point at a deleted project.
  Import from `@/integrations/supabase/client`.
- The repo permanently shows ~642 modified files. Pure CRLF. Never commit them.
- Type gate is `node_modules/.bin/tsc --noEmit -p tsconfig.app.json`. Plain
  `tsc` is a no-op and will tell you everything is fine while the app is broken.
- **A check that cries wolf is worse than no check.** Four separate false reds
  were fixed across 268 and 271. When one fires, measure whether it is true
  before believing it, and when it is false, fix the check and write down why.
- Do not ask Anthony what to build. Ask about money and the "Decision owed by
  Anthony" list in `docs/PROJECT-STATE.md`, and decide everything else yourself.
  The live-database question above is a genuine exception: it is irreversible and
  it bypasses his review pipeline.
